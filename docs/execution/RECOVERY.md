# Восстановление

Что и как откатить, если что-то из сделанного окажется неверным. Принцип везде
один: forward-only. Прикладные объекты не удаляются; ошибка чинится применением
правильного изменения, а не стиранием следа.

---

## Сверка реестра миграций Aether

**Что изменилось.** Вставлено 11 строк в
`supabase_migrations.schema_migrations`. Прикладных объектов операция не
касалась: дампы схемы до и после совпали побайтово (кроме одноразового nonce
самого `pg_dump`).

**Точка возврата.** Восстанавливать нечего — единственное изменение адресуемо
по именам:

```sql
delete from supabase_migrations.schema_migrations
where name in ('project_members','default_role_viewer','uploads','workspaces',
               'agent_registry','skill_packs','project_records',
               'records_freeform_status','kaiten_task_sync',
               'kaiten_webhook_inbox','n8n_bridge_outbox');
```

То же делает `python scripts/reconcile_migration_ledger.py --undo <файлы>`.

**Чего делать нельзя.** Удалять прикладные таблицы. Если предикат миграции
ложен, миграция чинится применением, а не подделкой строки реестра.

## Миграция 0019_agent_mcp_servers

**Что изменилось.** `alter table agents add column if not exists mcp_servers
text[];` и строка в реестре.

**Откат.** `alter table agents drop column mcp_servers;` — но только если код,

## Шифрование настроек

**Ключ.** `SETTINGS_ENCRYPTION_KEY`. **Его потеря необратима**: зашифрованные
значения восстановить будет нечем. Хранить в менеджере паролей.

**Откат кода без потери данных.** Значения в конверте `enc:v2:` читаются только
новым кодом. Поэтому возврат к прежней версии приложения требует, чтобы
перешифровка ещё не запускалась. Если она уже прошла — откат кода означает
потерю доступа к настройкам, и правильный путь другой: оставить новый код и
чинить конкретную ошибку.

**Ротация ключа.** Новый ключ в `SETTINGS_ENCRYPTION_KEY`, старый — в
`SETTINGS_ENCRYPTION_KEYS_RETIRED`, затем
`python scripts/rewrap_settings.py --apply`. Пока значение не переехало, оно
читается старым ключом, поэтому простоя нет. Скрипт отказывается завершиться
успешно, пока хоть одна строка осталась не на основном ключе.

**Если перешифровка прервалась.** Повторный запуск безопасен: он идёт одной
транзакцией под advisory-локом и внутри неё же проверяет, что не осталось строк
на чужом ключе. Частичный результат не фиксируется.

## Проверка сертификата БД

**Риск.** Если хост из `DATABASE_URL` не резолвится в IPv4 или его сертификат
подписан приватным центром, соединение после выката не установится.

**Быстрое смягчение.** `AETHER_DB_SSL_INSECURE=true` возвращает прежнее поведение
и пишет об этом в лог. Это временная мера.

**Правильное решение.** Перевести `DATABASE_URL` на хост пулера Supabase (его же
требует `docs/SETUP.md`) или подложить корневой сертификат через
`AETHER_DB_SSL_ROOT_CERT`.

## Одобрения (0020) и укрепление регистрации (0021)

**Откат — кодом, а не схемой.** Достаточно снять вызов `approvals.require_live`
в `send_result` и проверки в `approve_task`: поведение вернётся к прежнему, схему
трогать не нужно.

**Таблицу `task_approvals` не удалять.** Это аудиторский след; без работающего
кода она просто не пополняется. Колонка `tasks.created_by` пустая по умолчанию и
ничему не мешает.

**0021 обратима** повторным применением тела функции из `0009`: там роль читается
из `raw_user_meta_data`. Данные при этом не затрагиваются — триггер срабатывает
только на вставку в `auth.users`. Но это возвращает и дыру: самостоятельно
зарегистрировавшийся сможет выписать себе admin.

## Домен studio.selenasystems.com

**Что изменилось.** К Railway-сервису Aether добавлен второй custom domain.
`os.selenasystems.com` не тронут.

**Откат.** Удалить домен в Railway. На `os.` это не влияет: домены независимы.

**Пока DNS-записи нет** домен не подтверждён и трафик через него не идёт — то
есть состояние безопасно само по себе.

## Проект selena-os-staging

**Что создано.** Railway-проект `selena-os-staging`, Postgres 16 с томом, сервис
`migrate` без источника.

**Откат.** Удалить проект целиком. Он ни с чем не связан: отдельная база,
отдельные переменные, ни один существующий сервис на него не ссылается.

**Замечание.** Окружение внутри проекта называется `production` — это имя по
умолчанию у Railway. Контур определяется именем проекта, а не окружения.
