## 1. ~~Сертификат studio.selenasystems.com~~ — СНЯТ 2026-09-04

`verified: true`, сертификат `CERTIFICATE_STATUS_TYPE_VALID`, `os.` не затронут.

Причина залипания оказалась не в той записи, которую все проверяли. Railway
требует **две** DNS-записи, и вторая — `TXT _railway-verify.studio` —
никогда не создавалась. API её не показывает: в `dnsRecords` приходит только
CNAME, поэтому `errorMessage` был пуст, а статус честно показывал
`PROPAGATED` — проверялся лишь CNAME. Недостающая запись видна исключительно
глазами, в диалоге «Configure DNS Records» в панели.

Владелец пересоздала домен (новый id `1696026f-2cd5-48f4-b107-793a3e1f7e50`,
новая цель `ijo38eh1.up.railway.app`) и добавила обе записи в Vercel DNS.
Проверка с авторитетных серверов зоны — в `EVIDENCE/index.md`.

Осталось от гейта только одно: браузерная проверка входа, выхода, обновления
сессии и callback на новом адресе. Сертификат ей больше не мешает, но сетевая
политика этой среды к адресу не пускает — шлюз отвечает `403` на CONNECT.

## 2. ~~Корневой сертификат Supabase для Aether~~ — СНЯТ 2026-09-04

Владелец выгрузил `prod-ca-2021.crt` из дашборда своего проекта. Файл проверен
(самоподписанный корень `Supabase Root 2021 CA`, `CA=True`, собственная подпись
сходится), положен в `AETHER_DB_SSL_ROOT_CERT_PEM`, режим
`AETHER_DB_SSL_INSECURE` выключен. Деплой `ca6ad42d` поднялся без
`DB pool init failed` — и без `Interrupted-task cleanup skipped: RuntimeError`,
которая раньше падала именно из-за отсутствия пула. Полный разбор и сравнение
логов — в `EVIDENCE/index.md`, раздел «Проверка сертификата БД включена на
проде».

Осталась мелочь без срока: переменная `AETHER_DB_SSL_INSECURE` лежит со
значением `false`, а не удалена — операции удаления переменной у доступного
инструмента нет. На поведение это не влияет: код считает режим включённым
только при точном значении `"true"`.

## 3. Перевыпуск секрета моста

**Действие.** Заменить `SELENA_AETHER_BRIDGE_SECRET` у сервиса `receiver` и
`CONTROL_ROOM_BRIDGE_SECRET` у Aether. Обе стороны принимают список через
запятую: поставить новый первым, старый вторым, дождаться успешной доставки,
затем убрать старый — простоя не будет.

**Почему.** Владелец попросил выполнить перенос самостоятельно, а прочитать уже
установленное значение через API нельзя — оно скрыто. Поэтому значение было
сгенерировано в сессии и прошло через её протокол. Это секрет подписи, не
доступа к данным: им можно подделать событие для staging-приёмника, но нельзя
ничего прочитать.

## 4. ~~Ключи подписи для сервисов gateway и scanner~~ — СНЯТ 2026-09-04

Блокер снят не действием владельца, а изменением кода: gateway выпускает свою
пару Ed25519 сам при первом старте и оставляет приватную половину в базе, где
доступ решают гранты, а не договорённость.

Прежняя формулировка была верна по сути и неверна по выводу. Приватный ключ
действительно не должен появляться в протоколе сессии — но он не должен
появляться и в буфере обмена, менеджере паролей и логе деплоя, а именно туда он
попадал по дороге в панель хостинга. Правильный ответ — не «пусть его создаст
человек», а «пусть его никто не переносит руками».

Как устроено (миграция `0036`): таблица
`selena_release.gateway_signing_keys`, приватную колонку не читает никто, кроме
функции `ensure_gateway_signing_key`, права на которую есть только у
`selena_gateway_runtime`; публичную половину читают web и scanner — им нужно
проверять подпись. Две реплики, стартовавшие одновременно, не могут поставить
два ключа: транзакционный advisory-лок и уникальный индекс на живой ключ. Ключ
нельзя отозвать из рантайма — иначе рантайм мог бы заставить выпустить новый и
обесценить все ранее подписанные манифесты. Переменная
`SELENA_GATEWAY_SIGNING_PRIVATE_KEY` продолжает работать как override.

Проверено: 14 pgTAP-утверждений в `0036_gateway_signing_key_custody.pgtap.sql`
(весь прогон — 171 утверждение, 0 отказов) и 5 модульных тестов, включая
round-trip подписи ключом, который выпустил сам gateway.

## 5. Проверка восьми разделов Control Room в браузере

**Действие.** Открыть `https://web-production-6cb6b.up.railway.app` и пройти
восемь разделов.

**Почему не сделано исполнителем.** Сетевая политика этой среды не пропускает
`*.up.railway.app`: запрос отклоняется на прокси. Разделы проверены живым
запуском приложения на настоящей мигрированной схеме — но не на развёрнутом
контуре и не глазами.
