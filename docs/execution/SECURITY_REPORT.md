# Отчёт по безопасности

Значений секретов в документе нет — ни целиком, ни частями, ни в виде длины.

## Что было найдено и закрыто

### 1. Секреты интеграций лежали в базе открытым текстом

`app_settings` содержала 5 строк. Шифрование существовало в коде, но включалось
переменной `SETTINGS_ENCRYPTION_KEY`, которой в переменных сервиса нет: без неё
модуль работал в режиме pass-through, то есть писал значения как есть.

**Закрыто.** Шифрование обязательно: без ключа веб и воркер не поднимаются.
Значения хранятся в конверте `enc:v2:<метка ключа>:<токен>`; метка позволяет
понять, каким ключом зашифровано значение, не раскрывая ключ. Устаревшие формы
(plaintext, конверт `v1`, отозванный ключ) перезаписываются при первом же чтении,
массово — скриптом `rewrap_settings.py`.

Для локальной разработки остаётся явный опт-ин
`AETHER_ALLOW_PLAINTEXT_SETTINGS=true`, который не действует при
`APP_ENV=production`.

**Остаточный риск, который кодом не закрывается.** Значения уже лежали открытым
текстом в базе, а база попадала в резервные копии. Шифрование защищает будущее,
но не отменяет прошлого: пять credentials нужно перевыпустить у провайдеров.
См. `REMAINING_BLOCKERS.md` пункт 4.

### 2. Неудачная расшифровка молча возвращала шифротекст

Прежний `decrypt` при непроходящем токене возвращал значение как есть. То есть в
Telegram вместо токена бота уходила строка `enc:v1:...`, и сбой конфигурации
выглядел как сбой интеграции.

**Закрыто.** Теперь это `DecryptionError`. Покрыто тестом
`test_decrypt_raises_on_tampered_token` и `test_read_fails_closed_when_key_is_missing`.

### 3. Диагностика раскрывала конфигурацию анонимно

Шесть эндпоинтов `/health/*` отвечали без аутентификации. Из них два раскрывали
существенное:

- `/health/agent` отдавал последние четыре символа живого ключа авторизации
  агента и, через маску из точек по длине значения, его точную длину;
- `/health/db` отдавал текст исключения asyncpg — с хостом, портом и
  пользователем подключения.

**Закрыто.** Все диагностические эндпоинты требуют роль admin. Исключение —
`/health/db`: он отвечает и анонимно, потому что при недоступной базе войти
невозможно в принципе, но анонимный вызов получает только `ok`/`error`, а причину
видит администратор. Вместо хвоста ключа отдаётся отпечаток фиксированной длины.
`/health` остаётся публичным для uptime-проверок.

Тесты: `test_health_agent_requires_admin`,
`test_health_agent_does_not_leak_key_tail_or_length`,
`test_health_db_hides_exception_detail_from_anonymous`,
`test_other_diagnostics_require_admin`.

### 4. Токен Telegram-бота уходил в ответ пользователю

Токен — часть пути URL (`/bot<token>/sendMessage`), а текст исключения httpx
содержит URL запроса. Эта строка попадала в HTTP-ответ 400 любому редактору.

**Закрыто.** Появился модуль `app/core/redact.py`: он вычищает и явно переданные
значения, и типовые формы секретов в URL (токен бота, `user:password@` в DSN).
Применён к ошибкам Telegram и SMTP. Тесты
`test_telegram_transport_error_does_not_echo_bot_token`,
`test_telegram_error_body_is_scrubbed`.

### 5. Маска секрета в админке раскрывала длину и окончание

Прежняя маска повторяла длину значения точками и оставляла четыре последних
символа.

**Закрыто.** Маска постоянной ширины плюс восьмисимвольный отпечаток: отличить
одно значение от другого по-прежнему можно, восстановить — нет. Тест
`test_settings_preview_hides_value_and_length`.

### 6. Подлинность сервера базы не проверялась вовсе

Внешние подключения шли с `ssl.CERT_NONE` и выключенной проверкой имени. Канал
шифровался, но принимался любой сертификат от любого узла: посредник между
рантаймом и Supabase мог прочитать пароль базы и весь трафик.

**Закрыто.** Проверка сертификата — поведение по умолчанию. Подмена хоста на IP
(обход отсутствия IPv6) несовместима с проверкой и оставлена только в явном
режиме `AETHER_DB_SSL_INSECURE=true`, который сообщает о себе в лог уровня error.
Приватный корневой сертификат подкладывается через `AETHER_DB_SSL_ROOT_CERT`.

**Не проверено.** Цепочку сертификата живого хоста из песочницы подтвердить не
удалось — исходящий порт 5432 закрыт. Перед выкатом проверить на сервисе.

### 7. Роль при регистрации бралась из метаданных, которыми управляет пользователь

Проверка роли в Python уже читала только `app_metadata`, но триггер регистрации
заполнял `profiles.role` из `raw_user_meta_data`, а его пользователь задаёт сам
через клиент Supabase. Дальше сервер честно читал эту роль из `profiles` как из
источника правды. То есть при открытой регистрации можно было выписать себе
admin.

**Закрыто** миграцией `0021`: роль читается из `raw_app_meta_data`, который
пишется только через Admin API. Существующие пользователи не затронуты — триггер
срабатывает лишь на вставку в `auth.users`. Тесты
`test_signup_role_from_user_metadata_is_ignored`,
`test_admin_created_user_gets_role_from_app_metadata`.

### 8. Одобрение результата ничего не подтверждало

Одобрением была запись в `tasks.status`. Не проверялся исходный статус задачи;
автор задачи мог одобрить её сам; кто и что одобрил — не сохранялось; комментарий
одобряющего принимался схемой и выбрасывался; а отправка результата наружу
одобрение вообще не спрашивала.

**Закрыто** миграцией `0020` и политикой в `app/services/approvals.py`:
иммутабельная запись с актором, его ролью, решением, областью, отпечатком
одобренного содержимого и сроком; запрет удаления и любых правок кроме
однократного отзыва; автоотзыв при изменении результата или артефактов; переход
`pending_approval → approved` атомарно в той же транзакции, что и запись;
и обязательное действующее одобрение перед любой отправкой.

Пятнадцать тестов, из них девять негативных.

### 9. `.gitignore` не покрывал часть секретных файлов

Перечисление `.env`, `.env.local`, `*.local` не ловило `.env.production`,
`.env.staging`, а также `*.pem`, `*.key`, `*.p12` и файлы сервисных аккаунтов.

**Закрыто** глобом `.env*` с исключением для `*.example` и добавлением ключевых
расширений.

## Что проверено и оказалось чистым

- **Сканирование секретов** по рабочим деревьям и полной истории трёх
  репозиториев: 269 совпадений разобрано, **живых credentials — ноль**, секретов,
  которые были закоммичены и потом стёрты, — ноль. Единственный найденный
  ключевой материал — публичный по назначению anon-ключ Supabase.
- **Файлы окружения и сертификаты** ни в одном репозитории никогда не
  коммитились.
- **CORS**: значения по умолчанию безопасны (только localhost), wildcard теперь
  отвергается на уровне конфигурации, потому что рядом стоит
  `allow_credentials=True` — ошибка в одной переменной открыла бы API любому сайту
  от имени вошедшего пользователя.
- **Supply-chain-настройки** обоих JS-монорепозиториев целы и не ослаблялись.

| Риск | Состояние |
|---|---|
| Пять credentials в прошлом лежали открытым текстом | **Открыт до перевыпуска у провайдеров** — действие владельца |
| Пароль Postgres, который когда-то вставлялся в переписку | Открыт; не менялся этим прогоном |
| `bypassPermissions` у агентов рядом с `WebFetch` и пользовательскими загрузками | Открыт. Внешний текст доходит до модели из трёх направлений; отдельная работа, в объём ТЗ не входила |
| Токен сессии в query-строке для SSE и скачивания загрузок | Открыт; попадает в логи прокси и историю браузера |
| Нет lock-файла Python и верхних границ версий; нет сканирования зависимостей в CI | Открыт |
| Нет сканирования секретов в CI ни в одном из трёх репозиториев | Открыт. Деревья чисты сегодня, но ничто не мешает следующему коммиту |

Первые два закрываются только владельцем. Остальные — это работа, которую честнее
назвать и запланировать, чем сделать наспех внутри чужого этапа.
