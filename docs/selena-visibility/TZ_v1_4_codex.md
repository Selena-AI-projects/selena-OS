# TZ v1.4-codex — достройка кодом, автономный режим

Исполнитель: автономный кодинг-агент (Codex или аналог). Человек не отвечает на
вопросы по ходу работы. Всё, что требует решения владельца, вынесено в
«Жёсткие запреты» и «Вне скоупа» — остальное решается правилами по умолчанию из
этого документа, а принятое решение фиксируется в описании PR.

Цель: закрыть кодом всё, что в `IMPLEMENTATION_STATUS_MATRIX_v1_3.md` стоит как
`NOT_BUILT`, `DESIGNED` или «код есть, не доведено», кроме действий, которые
может совершить только владелец. Владелец параллельно готовит первый живой
прогон — Фаза 0 обслуживает именно его и делается первой.

## Инварианты дизайна (наследуются из v1.3, действуют во всех фазах)

- Никакого заголовочного общего балла. Пустая группа данных → `UNKNOWN`,
  никогда не «0%».
- Каждый вывод грунтуется в сохранённом evidence; рекомендация без evidence IDs
  не создаётся.
- Branded и non-branded считаются раздельно; смешанное маркируется `mixed`.
- Visitor View и API View не смешиваются в один показатель.
- Контекст (отзывы, каталоги) никогда не подаётся как причина ранжирования.
- VALID-прогон без экстракции — «неизмерено», не «нет упоминания».

## Жёсткие запреты (owner gates — нарушать нельзя ни при каких условиях)

1. **Не применять миграции.** Файлы миграций писать можно и нужно;
   `drizzle-kit migrate` не запускать. Каждая новая миграция — SQL-файл +
   запись в `meta/_journal.json`, нумерация продолжает существующую.
2. **Не включать живые адаптеры и не расширять allowlist**
   (`inertMeasurementAdapters` в
   `packages/selena-visibility-contracts/src/measurement-execution.ts`).
   Registry воркера остаётся `noop`.
3. **Не трогать секреты, бюджетные флаги и env-файлы деплоя.** Новые
   env-переменные объявлять в реестре (`packages/config/src/env-registry.ts`)
   с безопасным дефолтом «выключено».
4. **Не пушить в `release/*`.** Работа в ветке `codex/tz-v1-4` от текущего
   HEAD `release/selena-visibility-mvp`; на выходе — PR в эту ветку, не мерж.
5. **Ни одного реального вызова провайдера или платёжной системы** — в тестах,
   скриптах и при отладке. Верификация = юниты + stub-репетиция
   (`pnpm -C packages/lib rehearse:selena-stub-cycle` против локального
   Postgres).
6. **Не ослаблять supply-chain-контроль pnpm** (см. AGENTS.md). Новые
   зависимости не добавлять без крайней необходимости; если добавил — одна
   зависимость на PR-коммит с обоснованием.

## Правила автономной работы

- Малые атомарные коммиты, plain imperative без префиксов; changeset только на
  user-facing изменение.
- Тесты писать на наблюдаемое поведение (см. AGENTS.md), запускать точечно —
  только затронутые файлы; никаких полных прогонов линта.
- Неоднозначность в формулировках интерфейса решается по CABINET_MODEL:
  честнее показать `UNKNOWN` и закрытый шаг, чем придумать значение.
- Каждая фаза завершается обновлением своей строки в матрице статусов
  (Фаза 7). Если задача не удалась — статус в матрице пишется честно, работа
  продолжается со следующей задачи, а не останавливается.
- Тексты интерфейса — EN + RU, через существующий helper `tr()` в
  `apps/web/src/routes/_authed/app/selena.tsx` (или его вынесенный аналог).

## Фаза 0 — разблокировки для живого прогона (делать первой)

### 0.1 Tenant-ключи на `/api/v1/*`

Глобальный middleware (`apps/web/src/middleware/deployment.ts`, политики в
`apps/web/src/lib/auth/policies.ts`) требует `ADMIN_API_KEYS` раньше любого
хендлера, поэтому валидный ключ из `sv_api_keys` отвергается.

- Сделать: пропускать пути `/api/v1/selena/*` к их собственной
  ключевой аутентификации (`resolveApiKeyAuthContext`); админ-гейт остаётся на
  всех остальных `/api/v1/*`.
- Приёмка: юнит — запрос с валидным `sv_api_keys`-ключом к
  `/api/v1/selena/citation-gaps` проходит без `ADMIN_API_KEYS`; запрос без
  ключа — 401; админ-маршруты по-прежнему требуют админ-ключ.

### 0.2 Писатель profile-блока в Configuration Lock

`resolveExtractionContext` (`packages/lib/src/selena-extraction-context.ts`)
предпочитает profile-блок из lock-снапшота, но никто его не пишет — работает
только fallback на текущий профиль, то есть контекст экстракции может уехать
от того, что было продано.

- Сделать: при approve заказа (путь, где минтится Configuration Lock —
  `packages/lib/src/selena-visibility-repositories.ts`) снапшотить в lock блок
  профиля: brandName, варианты названия, owned-домены, конкуренты с доменами,
  `maps_location` (если есть).
- Приёмка: stub-репетиция читает контекст из lock-блока, а не из fallback;
  изменение профиля после approve не меняет контекст уже созданного цикла.

### 0.3 Хранение текста ответа + окно удаления (решение владельца Б)

Решение принято в `CABINET_MODEL.md` §4а: текст ответа храним в
`canonical_payload` записи прогона, 13 месяцев, затем автоматическое удаление
только сырого текста; находки/ссылка/дата остаются.

- Сделать: (а) в `RunOutcome`-путь и обоих live-адаптерах
  (`openrouter-measurement-adapter.ts`, `brightdata-measurement-adapter.ts`)
  добавить перенос тела ответа в `canonical_payload.answerText` при записи
  прогона — только тело ответа, тело ошибки провайдера не сохраняется никогда;
  (б) worker-джоба удаления текста старше 13 месяцев (по образцу
  `apps/worker/src/jobs/schedule-maintenance.ts`), удаляет только
  `answerText`, остальной payload не трогает, пишет audit-событие;
  (в) юнит: после «удаления» находки, citations и `rawResponseReference`
  на месте.
- Приёмка: stub-репетиция сохраняет текст; джоба с фиксированной датой
  вычищает только текст; тесты адаптеров подтверждают, что error body в
  payload не попадает.

### 0.4 Экран шага 4 «Замер» в клиентском кабинете

Движок и метрики готовы (`packages/lib/src/selena-ledger-metrics.ts`),
экрана нет — живой прогон будет невидим клиенту.

- Сделать: секция «Замер» в `/app/selena` (после «Проверка сайта»):
  статус цикла, ожидаемые/завершённые прогоны, mentionCoverage раздельно
  branded / non-branded, позиции, Visitor / API раздельно. Пустая группа —
  `UNKNOWN`. Шаг закрыт до заказа — показывается закрытым, не прячется
  (правило CABINET_MODEL §2).
- Приёмка: экран рендерит данные stub-репетиции; ни одного составного балла;
  `UNKNOWN` вместо нулей; юнит на серверную функцию выборки.

## Фаза 6 — перенос экранов Elmo внутрь маршрута (CABINET_MODEL §6)

старый маршрут для клиента закрывается. Порядок: Visibility/Share of Voice →
шаг 4; Citations → шаг 5; Opportunities → шаг 6; Prompts → шаг 2;
Settings → шаг 1. Query fan-out остаётся операторским.

- Приёмка: клиентская навигация не ведёт в `/app/$brand/*`; функциональность
  доступна внутри соответствующего шага; перенос экрана без переноса данных
  не считается выполненным.

## Порядок и критерий готовности

Фазы выполняются по номерам; внутри фазы задачи независимы. Работа считается
завершённой, когда: все фазы либо сделаны, либо честно помечены в матрице с
причиной; юниты и stub-репетиция зелёные; PR в
`release/selena-visibility-mvp` открыт с полным перечнем изменений и списком
env/миграций, которые владелец должен применить сам.
