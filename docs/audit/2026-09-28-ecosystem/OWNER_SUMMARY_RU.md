## Что работает (доказано на развёрнутом коде)
- Первая половина пути: вход → проект → задача → исполнитель → результат → мост → Inbox. Подпись,
  окно времени, идемпотентность, порядок версий, отказы моста — срабатывают; карточка приходит
  правильному владельцу, сквозной `trace_id` доходит до Inbox.
- Одобрение и очередь в Control Room; аварийный стоп реально блокирует выпуск на сервере.
- Изоляция в интерфейсе: чужая организация → 404, чужой отчёт клиента → отказ по арендатору, роли
  Aether через API → 403.
- Локальные инструменты: central-memory, ai-council, youtube-pro, публичный сайт.

## Что сломано (три главных разрыва)
1. **Доставка не работает нигде.** Шлюз выпусков с 3 сентября не может подписать манифест
   (`set_request_context` вызывается с 8 параметрами вместо 7 → 409) на всех развёрнутых коммитах.
   В изолированной песочнице однострочная правка доводит цепочку до публикации.
2. **Боевой контур не подключён.** Production-приёмник Control Room не получил ни одного запроса;
   события идут в staging-приёмник.
3. **Обратной связи нет.** Статус и метрики не возвращаются в Aether; результат задачи
   (`task.result.ready`) принимается, но не показывается в Inbox.

Отдельно и срочно (P0, детали — в приватном отчёте): в Aether есть дефекты контроля доступа к
чужим проектам; при переотзыве привязки возможен переток чужого черновика в кабинет другого
арендатора; в клиентском продукте аварийный стоп не останавливает платные вызовы бесплатной
проверки.

## Пять ближайших действий
1. Починить шлюз (одна строка) **и вместе с ним статус отказа `NOT_SENT`** — иначе отказ станет
   ложным «доставлено».
2. Закрыть дефекты контроля доступа в Aether (привязать объект к проекту/задаче из пути).
3. Решить топологию: какой Control Room — production, и переключить на него мост.
4. Развязать тупик одобрения в Aether (сейчас большинство задач одобрить некому: автор не может,
   участников нет).
5. Запустить присланный read-only SQL и завести тестовый аккаунт клиента — тогда закроются
   оставшиеся 3 проверки со входом.
