# SELENA OS — мастер-аудит, 2026-09-28 (публичная версия)

Эта версия безопасна для публичного репозитория. В ней нет деталей неисправленных уязвимостей,
production-данных и внутренних идентификаторов инфраструктуры. Полная версия с доказательствами
лежит в приватном репозитории `Selena-AI-projects/Aether-Medium`, ветка
`claude/selena-os-audit-2026-of5r10`, файл `docs/audit/2026-09-28/SELENA_OS_MASTER_AUDIT_2026-09-28.md`.

Исходный файл задания `SELENA_OS_Master_Audit_2026-09-28.md` в сессию не пришёл. Аудит выполнен
по тексту запроса и по плану, одобренному владельцем.

## Как проверялось

**Правила.** Production — только чтение: метаданные и логи Railway, агрегаты базы Aether, публичные
GET-запросы. Всё с записью шло в изолированной среде:
- отдельное сетевое пространство имён: только loopback, без DNS и выхода в сеть;
- временные кластеры PostgreSQL 16;
- код ровно тех коммитов, что развёрнуты: selena-OS `b437efc`, Aether `23ef430`,
  selena-ai-visibility `39dda8f`.

Реальных отправок, публикаций, платежей и вызовов моделей не было.

**Критерий GO.** Связь получает GO, только если выполнены три условия:
- в песочнице пройдены позитивный путь, отказ, повтор и изоляция;
- в production развёрнут тот же код;
- нужная настройка присутствует.

## Итог

**Сквозная цепочка — NO-GO.** Путь «вход → проект → задача → исполнитель → результат → мост →
Inbox» доказан на развёрнутом коде, включая реальный браузер (снимки в `evidence/screenshots/`).
Дальше цепочка обрывается:

1. **Доставка.** В `apps/worker/src/selena-release-gateway.ts` функция `withGatewayContext`
   отправляет `set_request_context($1…$7, NULL)` с восемью значениями. Postgres отвечает
   `bind message supplies 8 parameters, but prepared statement requires 7`. Из-за этого шлюз
   не может подписать ни один манифест: выпуск после 5 попыток уходит в dead-letter, остаётся
   `QUEUED`, а инцидент показывает только «409». Ошибка появилась в `8be855c` (2026-09-03) и есть
   во всех развёрнутых коммитах.
2. **Статус отказа.** `selena_release.record_postiz_submission_outcome` отвергает `NOT_SENT`,
   а диспетчер отправляет именно его на каждый отказ публикации. После исправления п. 1 отказ
   превратится в «COMPLETED» без отправки.
3. **Топология.** Production Aether доставляет события в staging-контур Control Room.
   Production-приёмник selena-os не получил ни одного запроса.
4. **Обратный канал.** Ни статус, ни метрики не возвращаются в Aether. Ожидание привязки проекта
   (в production до 11 часов) и навсегда потерянные события автор не видит.
5. **Результаты задач.** События `task.result.ready` принимаются и хранятся, но проекция забирает
   только `content.draft_ready`. Результат задачи никогда не появляется в Inbox. Это расходится с
   `docs/execution/COVERAGE.md:143,187`.

## selena-ai-visibility: подтверждено в песочнице

Всё ниже проверено на production-сборке коммита `39dda8f`, с веб-приложением под ролью
`selena_app`.

- **Бесплатная проверка идёт в обход аварийного стопа.** При `SELENA_EMERGENCY_STOP=true` и на
  вебе, и на воркере клиент запускает проверку, и воркер делает 2 авторизованных вызова
  провайдера. Проверено через локальную заглушку. Причина: ни
  `apps/worker/src/jobs/selena-free-ai-visibility.ts`, ни `sv_begin_free_ai_visibility_check`
  не смотрят на стоп.
- **Админский Inbox видит только свою организацию.** Фильтр в
  `apps/web/src/server/selena-order-requests.ts:260`: заявка из другой организации не видна.
- **Права роли расходятся с миграциями.** `packages/lib/scripts/selena-rls-runtime-role.sql`
  начинает с `REVOKE ALL` и не выдаёт заново права, которые миграции 0059–0067 выдают `selena_app`
  только при уже существующей роли. На свежей или восстановленной базе бесплатная проверка
  не работает: «We could not start or read this check».

**P0**
1. selena-OS: в `withGatewayContext` заменить `NULL` на `$8`; добавить интеграционный тест
   «шлюз ↔ настоящая БД».

   записывать отказ как `DEFINITIVE_FAILURE`.
3. selena-ai-visibility: проверять стоп и флаг в воркере бесплатной проверки до вызова
   провайдера, а на вебе — до резервирования бюджета.
4. Aether: исправить дефекты доступа (приватный репозиторий).
5. Владелец: решить, какой Control Room — production, и направить туда Aether; создать привязку

**P2.** Уборка инфраструктуры (копии БД и временные сервисы), перенос app.* в окружение
